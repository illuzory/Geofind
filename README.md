# Geofind · адреса и выезд по согласованию

MVP 0.3 анализа доступности площадок выездным сервисом. Один регион — Свердловская область. Пятнадцать площадок с полными адресами и точка инженеров по адресу **Россия, 620100, Свердловская область, г. Екатеринбург, переулок Буторина, д. 6**. Наименование «переулок» уточнено по реальному ответу OSM.

Оборудование и выбор адресов — испытательные данные. Дом и координаты найдены в OSM, но размещение оборудования по адресу не подтверждается. Проверка OSM не равна официальной проверке ФИАС/ГАР.

## Запуск

Python 3.12. Из каталога проекта в Linux:

```bash
./scripts/setup.sh
./scripts/start.sh
```

Сервер использует порт 8501, альтернативный — `PORT=8502 ./scripts/start.sh`. Для облачной среды используйте существующий checkout, дополнительный worktree не нужен. Live-процессы после восстановления среды необходимо запускать заново.

Для Windows: `py -3.12 -m venv .venv`, затем `.venv\Scripts\python -m pip install -r requirements.lock` и `.venv\Scripts\python -m streamlit run app.py`. Windows отдельно не проверялся.

По умолчанию без переменных подключения работает автономная дорожная модель Natural Earth. Она позволяет проверить импорт, адреса по сохранённым ответам и статистику без сети. Для автомобильных времён OSRM:

```bash
export OSRM_URL=https://router.project-osrm.org
export OSRM_CACHE_NAMESPACE=public-demo-$(date -u +%Y%m%dT%H%M%SZ)
./scripts/start.sh
```

Нажмите «Рассчитать дорожный сценарий». Первый сетевой расчёт может занять десятки секунд: публичный сервер ограничен одним запросом в секунду. Для регулярной/производственной нагрузки подключайте собственный OSRM и настоящую `OSRM_DATA_VERSION` графа/профиля. Публичный demo версии графа не сообщает, поэтому `OSRM_CACHE_NAMESPACE` обозначает только наблюдение/кэш клиента. Пробки не учитываются. Подробности и политика сервера — в docs/OSRM_VALIDATION.md.

## Три книги для проверки

| Файл | Площадки | Устройства | Общий SLA / по согласованию | Результат OSRM при 4 ч |
|---|---:|---:|---|---|
| data/ural_inventory.xlsx | 15 | 120 | 11 / 4 | 10 из 11 |
| examples/02_ural_changed_addresses.xlsx | 15 | 121 | 10 / 5 | 10 из 10 |
| examples/03_ural_changed_addresses.xlsx | 15 | 122 | 11 / 4 | 10 из 11 |

В архиве первая книга также продублирована в `examples/01_ural_base.xlsx`. В каждой следующей книге изменены все 16 адресов (15 площадок + инженеры), их координаты, типы отдельных площадок и количество устройств. `site_id` остаются постоянными.

Рост процента SLA во второй книге связан в том числе с переводом Серова в тип «по согласованию». Это не ускорение поездок: отдельный счётчик исключённых площадок остаётся видимым.

В пилоте: Екатеринбург, Нижний Тагил, Каменск-Уральский, Серов, Берёзовский, Ревда, Первоуральск, Верхняя Пышма, Асбест, Полевской, Реж, Невьянск, Кировград, Красноуфимск и Алапаевск. 54 записи прежнего регионального набора сохранены, добавлено 66 синтетических устройств — по 6 для 11 дополнительных городов. Города за пределами региона не перенесены по вымышленным адресам в Свердловскую область. Включённый в архив `source/equipment_inventory_original.xlsx` сохраняет полный первоначальный инвентарь отдельно, без изменений.

## Импорт в работающий сервис

1. Откройте исходную книгу, при OSRM нажмите кнопку первого расчёта.
2. Загрузите книгу 02 через «Обновить таблицы». Предпросмотр покажет адреса, типы и другие изменения.
3. Нажмите «Применить таблицу». При включённом «Пересчитывать после импорта» карта и показатели обновятся автоматически, без перезапуска.
4. Повторите с книгой 03: устройства изменятся 120 → 121 → 122, знаменатель SLA — 11 → 10 → 11, отдельные площадки — 4 → 5 → 4.
5. В разделе «Версии и восстановление» выберите исходную книгу и восстановите её.

Валидная книга сохраняется транзакционно в `.cache/runtime/imports.sqlite`. Повторное открытие сервиса использует последнюю активную версию. Неверный файл не заменит данные. Конкурирующий импорт с устаревшей версией отклоняется. Другую открытую сессию можно синхронизировать кнопкой «Обновить из хранилища». Путь меняется через `GEOFIND_STATE_DIR`, стартовая книга — через `GEOFIND_WORKBOOK` (для пустого хранилища). Если сервис уже запускался с восемью площадками, импортируйте новую `data/ural_inventory.xlsx`: обновление исходников не перезаписывает сохранённую пользователем версию автоматически.

## Два типа площадок

`Sites.service_type`:

- `standard`: участвует в общем SLA.
- `approval_required`: требуется согласование выезда. Фиолетовый маркер, отдельный слой и счётчик; исключена из числителя, знаменателя и максимума общего SLA.

Для согласуемой площадки всё равно считаются выбранный сервис, дорога и подготовка. Срок получения согласования не моделируется. `approval_note` — пояснение. Выдача разрешений/заявок, NetBox и уведомления не реализуются. В Services этот тип недопустим: поле относится к обслуживаемым площадкам, а не к местам выезда инженеров.

Зоны на карте показывают территориальное время доезда по общей сетке. Тип отдельного объекта не вырезает окружающую территорию из зоны покрытия. Пороги 4/6/8 часов настраиваются. Нулевой знаменатель отображается как «не применяется», а не 100%.

## Полные адреса и проверка

Книга содержит листы Equipment, Sites, Services, Readme. В Sites/Services:

| Поле | Назначение |
|---|---|
| site_id | постоянный ID; уникален, сервисы и клиенты имеют разные ID |
| name | название; Equipment.Site Name должно совпадать |
| country, region, city, street, house | структурированный адрес |
| postal_code | необязательный индекс; при заполнении сверяется с OSM |
| address | полный читаемый адрес, согласованный с компонентами |
| latitude, longitude | координаты; региональные объекты проверяются по границе |
| service_type, approval_note | тип площадки и пояснение согласования |
| is_demo | признак испытательного местоположения/сценария |

В Equipment добавлен `Site ID`, который проверяется на соответствие имени. Первые шесть полей исходной таблицы сохранены. Старые книги без service_type читаются как standard; при наличии столбца неизвестный/пустой тип отклоняется. Вычисляемые status/sla_eligible и статусы проверки из файла не принимаются как решение системы.

Откройте «Проверка адресов и координат» → «Проверить адреса». Проверяются формат, согласованность полного адреса с компонентами, город/регион/улица/дом по OSM и расстояние от координаты до найденного объекта. Тип улицы значим: улица и переулок не подменяются друг другом. Допуск координат — 250 м; географическое нахождение в области само по себе не подтверждает адрес.

Для всех 48 адресов трёх книг сохранены реально полученные ответы OSM (`data/address_reference.json`), поэтому примеры проверяются без сети. Отчёт всегда показывает источник и дату ответа. Для нового адреса включите «Онлайн-проверка новых адресов». Для свежей проверки уже известного адреса дополнительно включите «Повторно проверить известные адреса онлайн» — сохранённый ответ и кэш будут обойдены. `GEOCODER_URL` позволяет подключить свой Nominatim-совместимый сервер. На публичном Nominatim запросы идут не чаще одного в 1.1 секунды, без автодополнения, до 30 адресов за запуск; ответы кэшируются 7 дней. Для массовой/производственной проверки нужен свой провайдер. Онлайн-доступ к геокодеру не требуется для поставляемых примеров.

Статусы «не найден», «несколько объектов», «не совпали детали», «расходятся координаты», «ещё не проверено» и «геокодер недоступен» различаются. Последний не означает неверный адрес. Можно скачать отчёт и открыть предложенную точку на OSM.

Проверка отрицательного сценария: в копии книги сдвиньте одну широту на 0.02, оставив адрес. Загрузите её и проверьте адреса: одна координата будет отмечена как несоответствующая. Система предложит точку из OSM, но изменит её только после «Применить предложенные координаты». Будет создана отдельная версия и обновлён маршрут.

## Воспроизведение генерации

Для повторной генерации можно использовать сохранённые проверенные ответы без сети:

```bash
.venv/bin/python scripts/prepare_address_examples.py --discovery data/address_reference.json --source data/ural_inventory.xlsx
```

Существующее оборудование сохраняется; повторная генерация базовой книги не дублирует устройства. Идентификаторы площадок стабильны между тремя вариантами. Даты уже сохранённых геокодерных ответов не подменяются датой генерации.

## Проверка и артефакты

```bash
.venv/bin/python -m pytest -q
.venv/bin/python scripts/validate_release.py --backend demo
# Явная сетевая проверка OSRM:
.venv/bin/python scripts/validate_release.py --backend osrm
# При запущенном отдельном сервере на 8502 с исходной книгой:
.venv/bin/python scripts/browser_address_release.py --port 8502 --backend osrm
```

В `snapshots/` архива находятся карты, CSV, отчёты и скриншоты проверенной версии. HTML — снимок карты; импорт и пересчёт доступны в приложении. Старые scripts/browser_smoke.py и validate_osrm.py рассчитаны на прежний четырёхплощадочный пример.

## Границы готовности

Проверен 61 автоматический тест, реальный OSRM для трёх книг, геокодер онлайн и полный браузерный цикл импорта/исправления/восстановления. Документированные результаты — docs/15_SITE_VALIDATION.md. Ресурсные ограничения: один регион, до 10000 ячеек, 10 сервисов и 2000 площадок; публичному OSRM — до 1000 ячеек и 3 сервисов. Клиент проверялся с ограничением адресного пространства 16 ГиБ. Память удалённого OSRM не измерялась.

Это MVP с более строгими данными и восстановлением версий. До промышленного развёртывания нужны авторизация и разграничение доступа, резервное копирование/эксплуатация БД, собственные маршрутизатор и геокодер, при необходимости официальная проверка ГАР/ФИАС. Пробки, погода, загрузка инженеров, ремонт и срок согласования не моделируются. Геометрия зон приблизительная, по представительным точкам сетки.

Рабочая ветка проекта: `feat/regional-sla-dashboard`. `main` обновляется через Pull Request. Исходный приватный файл и runtime-хранилище не включаются в Git.
